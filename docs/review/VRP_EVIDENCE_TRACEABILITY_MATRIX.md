## 1. Purpose

This document establishes the public evidence traceability framework for the Veil Routing Protocol (VRP).

Its purpose is to provide a verifiable relationship between:

1. Protocol security requirements.
2. Declared architectural invariants.
3. Adversarial test scenarios.
4. Expected runtime behavior.
5. Observed execution results.
6. Evidence artifacts.
7. Verification verdicts.
8. Residual limitations.

The central requirement is:

**EVERY SECURITY CLAIM MUST HAVE AN IDENTIFIABLE VERIFICATION PATH.**

A declared invariant is not automatically an experimentally verified property.

A passing test is not automatically proof of production readiness.

An independently executable model is not automatically evidence of a deployed runtime.

This document explicitly separates these categories.

---

## 2. Architectural Assurance Model

VRP follows a continuity-first architectural principle:

**SESSION != TRANSPORT**

The logical session is not defined exclusively by its current network transport.

However, continuity must not compromise security.

The following assurance relationships are fundamental:

**CONTINUITY REQUIRES IDENTITY INTEGRITY.**

**MIGRATION REQUIRES VALID AUTHORITY.**

**REJECTION MUST NOT CAUSE UNAUTHORIZED COMMIT.**

**RECOVERY MUST PRESERVE CANONICAL HISTORY.**

**EVIDENCE MUST BE ATTRIBUTABLE TO AN IDENTIFIED IMPLEMENTATION.**

Each relationship must be evaluated independently.

## 3. Verification Status Vocabulary

Every verification record must use one of the following statuses.

| Status | Definition |
|---|---|
| PASS | All scoped acceptance conditions satisfied |
| FAIL | At least one required condition violated |
| INCONCLUSIVE | Evidence insufficient to establish a verdict |
| NOT RUN | Test not executed |
| BLOCKED | Execution prevented by an identified prerequisite |
| MODEL PASS | Public reference model passed; runtime behavior not established |
| REGRESSION PASS | Previously failing scenario passed after remediation |

A verdict must be associated with an explicit evidence scope.

For example:

`MODEL PASS` does not imply `INTEGRATED RUNTIME PASS`.

Similarly:

`REGRESSION PASS` does not establish that unrelated attack classes have been eliminated.

## 4. Evidence Classification

### E0 — Specification Evidence

Published contracts and intended protocol behavior.

### E1 — Reference Model Evidence

Executable public models demonstrating individual invariants.

### E2 — Runtime Evidence

Tests executed against an identifiable implementation revision.

### E3 — Integrated System Evidence

Tests involving the runtime, transport, operating system and relevant application behavior.

### E4 — Independent Reproduction

Evidence generated by an independent evaluator using an identifiable test artifact and documented methodology.

### E5 — Operational Qualification

Deployment-specific validation against formally agreed operational requirements.

Evidence classifications describe scope, not automatic trustworthiness.

A higher evidence class still requires complete, authentic and relevant supporting records.

## 10. RED-to-GREEN Remediation Traceability

A security correction must preserve the relationship between the original failure and the final passing result.

### Required remediation record

**Finding ID:**

Unique security finding identifier.

**Affected invariant:**

Reference to the invariant register.

**Original failure:**

A reproducible description of the violated contract.

**RED evidence:**

Artifact proving the failure existed.

**Correction scope:**

Public description of the affected behavior without disclosing protected implementation.

**GREEN evidence:**

Artifact proving the original test passes against the corrected revision.

**Regression evidence:**

Tests demonstrating that related behavior remains valid.

**Residual risk:**

Known limitations or untested scenarios.

**Revision identity:**

Source and artifact identity before and after remediation.

### Required transition

RED  
-> SCOPED CORRECTION  
-> GREEN  
-> REGRESSION  
-> EVIDENCE VERIFICATION

A successful correction must not erase the historical failure record.

The remediation chain should remain auditable.

## 11. Independent Session Identity Oracle

VRP's foundational claim requires special verification treatment.

**SESSION != TRANSPORT**

A valid continuity test cannot rely exclusively on:

- Process survival.
- Socket survival.
- Interface persistence.
- UDP reconnection.
- Successful packet delivery.
- Recreated tunnels.

The test must independently establish whether the same logical session persists.

### Required observation tuple

    session_identity
    transport_identity
    authority_state
    canonical_state
    application_progress
    recovery_timestamp

The observation mechanism must be sufficiently independent of the transport event being evaluated.

### Required comparison

**Before disruption:**

Capture the logical-session identity and relevant state.

**During disruption:**

Capture the transport change or failure.

**After recovery:**

Capture the logical-session identity and verify applicable security postconditions.

### Verdict rules

**PASS:**

The independent identity observation confirms continuity and all required postconditions hold.

**FAIL:**

The logical session changes unexpectedly or a required security invariant is violated.

**INCONCLUSIVE:**

The test demonstrates reconnection but does not independently establish logical-session continuity.

## 12. Compound Failure Validation

Single-fault success does not establish multi-fault correctness.

VRP should be evaluated under combinations of:

- Endpoint churn.
- Packet loss.
- Reordering.
- Replay pressure.
- Transport blackout.
- Authority contention.
- Resource pressure.

### Proposed stress profiles

| Profile | Conditions |
|---|---|
| CP-01 | Endpoint churn every 2 seconds |
| CP-02 | 30% packet loss |
| CP-03 | 50% packet loss |
| CP-04 | 80% packet loss |
| CP-05 | 90% packet loss |
| CP-06 | 10-second blackout |
| CP-07 | 30-second blackout |
| CP-08 | 60-second blackout |
| CP-09 | RTT 300–900 ms with jitter and reordering |
| CP-10 | Endpoint churn + 80% loss + blackout + replay |

These profiles are proposed validation configurations.

They are not published PASS results.

Each profile requires:

1. Independent session-identity observation.
2. Authority-integrity verification.
3. Replay-containment verification.
4. Application-delivery measurement.
5. Recovery-time measurement.
6. Resource-consumption measurement.
7. Explicit final verdict.

## 13. Evidence Artifact Requirements

Each test execution should produce a dedicated evidence directory.

Recommended structure:

    evidence/
      <campaign-id>/
        MANIFEST.md
        BUILD_INFO.txt
        SOURCE_IDENTITY.txt
        TEST_CONFIGURATION.json
        EXPECTED_RESULTS.md
        EXECUTION.log
        OBSERVED_RESULTS.json
        VERDICT.md
        SHA256SUMS

For public publication, sensitive paths, credentials, tokens and proprietary implementation details must be removed or redacted.

Redaction must not alter the meaning of the reported result.

### Integrity requirements

Evidence artifacts should be immutable after finalization.

A published manifest should identify the artifacts included in the evidence set.

Checksums should be generated after finalization and verified before publication.

The evidence set must not claim cryptographic authenticity unless an appropriate trusted signature mechanism is actually used.

## 14. Test Verdict Contract

A formal PASS verdict requires:

**PRECONDITIONS VERIFIED**

The evaluated system starts from the required state.

**ATTACK EXECUTED**

The intended adversarial stimulus is demonstrably applied.

**EXPECTED REJECTION VERIFIED**

Prohibited behavior is rejected.

**CANONICAL STATE VERIFIED**

No unauthorized persistent mutation occurs.

**POSITIVE CONTROL VERIFIED**

Legitimate work remains possible where required.

**ARTIFACT IDENTITY VERIFIED**

The result is tied to the evaluated revision.

**EVIDENCE INTEGRITY VERIFIED**

The published record matches its integrity references.

**LIMITATIONS RECORDED**

The scope of the result is explicit.

If a required condition is missing, the test must not be silently marked PASS.

## 15. Independent Reviewer Procedure

A reviewer should perform the following operations.

### Step 1 — Identify the claim

Select a stable VRP invariant ID.

### Step 2 — Identify the test

Locate the corresponding test ID and expected postconditions.

### Step 3 — Identify the artifact

Verify the source revision, build identity and relevant test environment.

### Step 4 — Reproduce the test

Execute the documented procedure when public artifacts are available.

### Step 5 — Verify negative behavior

Confirm that prohibited operations are rejected.

### Step 6 — Verify positive behavior

Confirm that legitimate operations remain valid where required.

### Step 7 — Inspect evidence integrity

Validate checksums, signatures where applicable, and artifact consistency.

### Step 8 — Assign a scoped verdict

Record PASS, FAIL, INCONCLUSIVE, NOT RUN or BLOCKED.

### Step 9 — Record limitations

Explicitly document what the evaluation did not establish.

Independent reviewers must not infer protected runtime behavior from public reference-model results.

## 16. Assurance Coverage Accounting

Coverage must be reported separately for:

- Specification coverage.
- Public reference-model coverage.
- Runtime test coverage.
- Integrated system coverage.
- Independent reproduction coverage.
- Operational qualification coverage.

### Suggested metrics

**Invariant coverage:**

    verified_invariants / applicable_invariants

**Test execution coverage:**

    executed_tests / planned_tests

**Passing test ratio:**

    passed_tests / executed_tests

**Independent reproduction coverage:**

    independently_reproduced_tests / eligible_tests

These metrics must not be combined into an unsupported universal security score.

Coverage denominators and exclusions must be disclosed.

A test count is not a substitute for threat coverage.

## 17. Public Disclosure Boundary

This matrix intentionally exposes:

- Security requirements.
- Stable invariant identifiers.
- Test categories.
- Expected observable behavior.
- Evidence requirements.
- Verification methodology.
- Scoped results.
- Known limitations.

It intentionally excludes:

- Protected Core algorithms.
- Private authorization mechanisms.
- Proprietary state-transition implementation.
- Secret material.
- Internal defensive decision logic.
- Sensitive deployment configuration.
- Non-public exploit details.

Independent evaluation can be supported through observable contracts without unrestricted access to protected intellectual property.

## 18. Release Qualification Policy

A public release should not be described as enterprise-qualified unless the applicable acceptance requirements have been met.

At minimum, a qualification statement should identify:

- Evaluated version.
- Source identity.
- Evidence bundle.
- Applicable invariants.
- Passed scenarios.
- Failed scenarios.
- Inconclusive scenarios.
- Untested scenarios.
- Deployment limitations.
- Review authority.

A release can be suitable for research validation without being qualified for critical infrastructure deployment.

These are distinct engineering milestones.

## 20. Final Assurance Statement

The purpose of this matrix is not to maximize the number of reported PASS results.

Its purpose is to ensure that every published security claim has an identifiable verification path.

VRP engineering assurance depends on:

**DEFINED INVARIANTS**

**REPRODUCIBLE ADVERSARIAL TESTS**

**CANONICAL STATE VERIFICATION**

**INDEPENDENT SESSION IDENTITY OBSERVATION**

**ATTRIBUTABLE EVIDENCE**

**EXPLICIT LIMITATIONS**

A protocol should be evaluated by the behavior it demonstrates under failure, not merely by the behavior it exhibits under ideal conditions.

**SESSION != TRANSPORT**

**REJECTION != PARTIAL COMMIT**

**REACHABILITY != AUTHORITY**

**RECONNECTION != VERIFIED CONTINUITY**

**TEST SUCCESS != UNIVERSAL SECURITY PROOF**

**EVIDENCE BEFORE CLAIMS.**
